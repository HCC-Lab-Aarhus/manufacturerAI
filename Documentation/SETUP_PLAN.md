# Setup Plan — Firmware Generation Agent

## Overview

After the manufacturing pipeline produces a physical device (3D-printed enclosure, silver-ink traces, inserted components), we need a **Setup** step that generates firmware for the microcontroller so the device actually does what the user asked for.

Currently, firmware generation is hardcoded to a single use case (Universal IR Remote template with pin substitution). The Setup step replaces this with a general-purpose **LLM firmware agent** that can write Arduino code for _any_ device the pipeline produces.

## Why an LLM Agent (not a template system)

The current firmware generator only handles one device archetype (IR remote). Every new device type would need a new handwritten template. An LLM agent solves this because:

1. **Infinite device variety** — A flashlight, a remote, a timer, a game controller, a sensor logger — each needs completely different firmware logic. The agent derives behavior from the user's original description.
2. **Library selection** — The agent picks the right Arduino libraries for each component (IRremote, Servo, Wire, SPI, etc.) based on what's in the circuit.
3. **Behavioral reasoning** — "4-button remote" implies button-press → IR-send mapping. "LED flashlight with brightness control" implies PWM + button state machine. The agent infers this from context rather than us coding every permutation.
4. **Pin-aware code** — The router already computed exact Arduino pin numbers. The agent receives these as structured data and writes code using them directly — no guessing, no conflicts.

---

## What the Setup Agent Receives

The agent gets everything it needs from the previous pipeline stages:

### From design.json
- `device_description` — The user's original intent in 2-4 sentences (e.g., "A slim TV remote with power, volume up/down, and 5 channel buttons, plus an IR LED and a status LED")
- `ui_placements` — Which buttons/LEDs exist and their instance IDs

### From circuit.json
- `components[]` — Every component with catalog_id, instance_id, config (resistor values, LED wavelength, etc.)
- `nets[]` — Electrical connections ("BTN_PWR" connects btn_1:pin1 to mcu_1:PD2)

### From routing.json (pin assignments)
- `pin_assignments` — The router's final MCU pin mapping:
  ```
  btn_1  → PD2  (Arduino pin 2)
  btn_2  → PD3  (Arduino pin 3)
  led_1  → PB1  (Arduino pin 9, PWM capable)
  ir_1   → PD6  (Arduino pin 6, PWM capable)
  ```
- This is the ground truth for which physical Arduino pin connects to which component.

### From catalog (component specs)
- Pin definitions, electrical characteristics, and behavioral notes for each component type (e.g., "IR LED requires 38kHz PWM carrier").

## How the Setup Agent Works

### Step 1: Build the Behavioral Spec (automatic, pre-agent)

Before the LLM runs, we programmatically assemble a **behavioral context document** from the pipeline artifacts. This isn't generated by the LLM — it's deterministic extraction:

```
DEVICE: "Slim TV remote with power, volume, channel buttons, IR LED, status LED"

COMPONENTS & PIN MAP:
  btn_power   → Arduino pin 2  (INPUT_PULLUP, active LOW)
  btn_vol_up  → Arduino pin 3  (INPUT_PULLUP, active LOW)
  btn_vol_down→ Arduino pin 4  (INPUT_PULLUP, active LOW)
  btn_ch1     → Arduino pin 5  (INPUT_PULLUP, active LOW)
  btn_ch2     → Arduino pin 7  (INPUT_PULLUP, active LOW)
  led_status  → Arduino pin 9  (OUTPUT, PWM capable)
  ir_led      → Arduino pin 6  (OUTPUT, PWM carrier needed)
  resistor_1  → (current limiter for led_status, 220Ω)
  resistor_2  → (current limiter for ir_led, 100Ω)

POWER:
  Battery: 2xAAA (3V nominal)
  MCU: ATmega328P running at 8MHz internal oscillator (no crystal)

NETS (logical groupings):
  VCC: battery+ → mcu VCC → mcu AVCC
  GND: battery- → mcu GND → all component grounds
  BTN_PWR: btn_power:pin2 → mcu:PD2
  IR_DRIVE: mcu:PD6 → resistor_2 → ir_led:+
  ...
```

This gives the LLM a clean, structured summary rather than raw JSON blobs.

### Step 2: LLM Firmware Agent (the creative step)

The agent receives:
- **System prompt** describing its role: "You are an embedded firmware engineer. Write a complete Arduino sketch (.ino) for the device described below. Use the exact pin numbers provided. Do not invent pins or components that aren't listed."
- **The behavioral context document** from Step 1
- **Constraints & rules:**
  - Target: ATmega328P (Arduino-compatible, avr-gcc)
  - Use only standard Arduino core functions + well-known libraries
  - All buttons use INPUT_PULLUP (no external pull-ups on the PCB)
  - Include debounce logic for tactile switches
  - Include power-saving where appropriate (sleep modes for battery devices)
  - Code must be a single .ino file (no multi-file sketches)
  - Add a brief comment header listing the pin map for human reference

The agent writes the complete firmware in one tool call (`submit_firmware`).

### Step 3: Compile & Fix Loop

This is the key reliability mechanism — inspired by SeedGPT's build→fix cycle:

```
┌─────────────────┐
│ Agent writes .ino│
└────────┬────────┘
         ▼
┌─────────────────┐
│ Compile with     │
│ arduino-cli      │
│ compile          │
│ --fqbn            │
│ arduino:avr:uno  │
└────────┬────────┘
         │
    ┌────┴────┐
    │ Success? │
    └────┬────┘
     YES │    NO
     ▼        ▼
  Done    ┌──────────────┐
          │ Feed errors   │
          │ back to agent │
          │ "Fix these    │
          │  compile      │
          │  errors: ..." │
          └──────┬───────┘
                 ▼
          Agent rewrites
          (up to 3 retries)
```

**Compilation tool:** `arduino-cli` (installable, headless, CI-friendly).
- Board FQBN: `arduino:avr:uno` (compatible with ATmega328P)
- We compile but don't upload — the user handles flashing separately
- Compiler errors are captured and fed back verbatim to the agent

**Why this works:** LLMs are good at writing ~90% correct Arduino code on the first try. The remaining 10% is usually syntax issues, missing includes, or wrong function signatures — exactly the kind of errors that are easy to fix when you see the compiler output. 3 retries is usually more than enough.

### Step 4: Output

On successful compilation, the step produces:

```
outputs/web/run_YYYYMMDD_HHMMSS/
├── firmware.ino              # The generated Arduino sketch
├── firmware_build/           # Compiled binary artifacts
│   ├── firmware.ino.hex      # Flash-ready HEX file
│   └── firmware.ino.elf      # Debug symbols (optional)
└── manifest.json             # Updated with firmware metadata
```

The `.hex` file is what gets flashed onto the ATmega328P — either via ISP programmer, FTDI adapter, or bootloader upload.

## Agent Design Details

### System Prompt Structure

```
ROLE:
  Embedded firmware engineer writing Arduino sketches.

DEVICE CONTEXT:
  {behavioral_context_document}

RULES:
  1. Use ONLY the pin numbers listed above. Never invent new pins.
  2. Every button must have software debounce (minimum 50ms).
  3. Use INPUT_PULLUP for all tactile switches (no external pull-ups exist).
  4. Prefer standard Arduino functions (digitalWrite, analogRead, etc.).
  5. For IR: use the IRremote library (version 4.x API).
  6. For power saving: use avr/sleep.h if the device is battery-powered.
  7. Keep it simple — no RTOS, no complex state machines unless the
     device behavior genuinely requires it.
  8. Add a comment block at the top with: device name, pin map, and
     a 1-line description of what each button/LED does.

OUTPUT:
  Call submit_firmware(code) with the complete .ino file contents.
```

### Tool: `submit_firmware`

Single tool — takes the raw .ino source code as a string. The pipeline:
1. Saves to `firmware.ino` in the session directory
2. Runs `arduino-cli compile`
3. If compile fails → returns error messages to agent for retry
4. If compile succeeds → saves .hex, updates manifest, marks step complete

### Library Management

The agent's system prompt should include a **known-good library list** that we've pre-installed in the arduino-cli environment:

| Component Type    | Library                | Include            |
|-------------------|------------------------|--------------------|
| IR LED / Receiver | IRremote 4.x           | `<IRremote.hpp>`   |
| Servo motor       | Servo (built-in)       | `<Servo.h>`        |
| I2C devices       | Wire (built-in)        | `<Wire.h>`         |
| SPI devices       | SPI (built-in)         | `<SPI.h>`          |
| OLED display      | Adafruit SSD1306       | `<Adafruit_SSD1306.h>` |
| Neopixels         | Adafruit NeoPixel      | `<Adafruit_NeoPixel.h>` |
| Temperature       | OneWire + DallasTemp   | `<OneWire.h>`      |

We preinstall these via `arduino-cli lib install` so compilation doesn't fail on missing dependencies. The list grows as we add new component types to the catalog.

## Device Simulation (Interactive Testing — Real AVR Emulation)

After firmware is generated and compiled, the user should be able to **test the device in the browser** before printing anything. Click a button, see an LED light up, read "IR signal sent" in a log. This must be a **real program running the real compiled firmware** — not an LLM approximation of what it thinks the code does.

### The Core Idea: simavr Running the Actual .elf

**simavr** is an open-source, cycle-accurate ATmega328P emulator written in C. It loads the actual compiled `.elf` binary (which we already produce from the compile step) and executes it instruction-by-instruction — the same instructions that would run on the physical chip. No guessing, no behavioral approximation, no LLM involved.

We build a **test harness** around simavr that:
1. Loads the `.elf` file
2. Wires up virtual peripherals (buttons, LEDs, IR) to the correct GPIO pins (from `routing.json`)
3. Accepts input events ("button X pressed") from the frontend
4. Reports output state changes ("pin 9 went HIGH → led_status is ON") back to the frontend
5. Runs in real-time (or faster) on the server

This is **the same code that runs on the real chip**, just running in software instead of on silicon.

### Why Real Emulation (not an LLM behavioral twin)

- **Truthful.** The emulator runs the actual compiled binary. If there's a bug in the firmware (wrong pin, missing debounce, broken state machine), the simulation shows the bug — it doesn't paper over it with what the LLM "thinks" should happen.
- **No drift.** The firmware .elf IS the simulation. There's nothing to get out of sync.
- **Catches real bugs.** Infinite loops, uninitialized variables, wrong interrupt handlers, timing issues — all show up in the emulator because it's executing real AVR instructions.
- **Library code runs too.** IRremote, Servo, Wire — their actual compiled code runs in the emulator. An LLM twin would have to fake library behavior.

### The simavr Harness

A small C program (~200 lines) that:

1. **Initializes simavr** with ATmega328P at 8MHz (matching our internal-oscillator setup)
2. **Loads the .elf** — simavr reads the compiled binary including debug symbols
3. **Attaches virtual peripherals** based on a pin-map config file:
   - **Buttons:** IRQ callbacks on input pins — when the harness receives a "press btn_power" command, it drives pin PD2 LOW (INPUT_PULLUP means active LOW). On "release," drives it HIGH.
   - **LEDs:** IRQ listeners on output pins — when the firmware writes HIGH to PB1, the harness reports "led_status: ON." PWM outputs report duty cycle (0–255).
   - **IR LED:** Listens on the Timer/OC pin for 38kHz PWM bursts. When it detects a modulated signal, it reports "IR transmitting" + duration. (simavr has timer peripheral support built in.)
4. **Runs a command loop:**
   ```
   while running:
     read JSON command from stdin  (button press/release, reset, quit)
     inject pin state change into simavr
     run simavr for N cycles (e.g., 100ms worth = 800,000 cycles at 8MHz)
     read all output pin states
     write JSON state update to stdout
   ```
5. **Handles timing:** The firmware's `delay()` and `millis()` work correctly because simavr simulates the Timer0 peripheral that Arduino's timing functions rely on. A 50ms debounce delay in the firmware = 400,000 simulated cycles.

The harness reads a `sim_config.json` generated from routing.json's pin assignments:

### Simulation Manager (Python)

The Python backend manages the simavr harness process:

```
class SimulationManager:
    """
    Manages the lifecycle of a simavr harness subprocess.
    One instance per active session with firmware.
    """

    start(session_dir):
        1. Generate sim_config.json from routing.json pin assignments
        2. Spawn harness subprocess: ./simavr_harness sim_config.json
        3. Wait for "ready" message on stdout
        4. Open WebSocket connection to frontend

    handle_input(event):
        # Frontend sends: {"action": "press", "instance_id": "btn_power"}
        1. Map instance_id → port/pin via sim_config
        2. Send JSON command to harness stdin
        3. Read state update from harness stdout
        4. Forward pin state changes to frontend via WebSocket

    stop():
        1. Send "quit" to harness stdin
        2. Kill subprocess
        3. Clean up WebSocket
```

#### Why a Subprocess (not in-process)

simavr is a C library. We could use Python ctypes/cffi bindings, but a subprocess is simpler and safer:
- **Isolation** — if the firmware has an infinite loop or crashes the VM, we just kill the process. No risk to the Python server.
- **No build complexity** — we compile the harness once as a standalone binary. No Python C extension build chain.
- **Language-agnostic** — the JSON stdin/stdout protocol means we could later swap the Python manager for Node.js or anything else.

- **Step mode** lets the user advance the simulation by 1ms at a time, useful for debugging timing-sensitive firmware (debounce, IR carrier pulses).

The viewport additions are the same regardless of emulation backend:

2. **Hover highlight** — Soft glow + pointer cursor on interactive components.
3. **LED glow** — Emissive material driven by pin state from simavr. HIGH = glow, LOW = dark. PWM duty cycle maps to emissiveIntensity (0–1).
4. **Button animation** — Depress on mouse-down, spring back on mouse-up.
5. **IR flash** — Brief purple flash on IR LED mesh when simavr reports carrier output.

### Handling simavr's Quirks

#### Arduino Library Support

The compiled .elf already contains Arduino core code (digitalWrite, analogRead, delay, millis, etc.) — these are compiled into the binary and work in simavr because they're just AVR register operations that simavr faithfully simulates.

For **IRremote**: The library generates 38kHz PWM via Timer2 and OC2B. simavr's Timer2 peripheral model handles this. The harness listens for timer compare-match IRQs to detect IR transmission windows.

#### No Serial Monitor (yet)

If the firmware uses `Serial.print()` for debugging, simavr can capture UART output and forward it to the log panel. This is a natural extension — simavr has built-in UART peripheral support. Nice to have but not required for v1.

#### Infinite Loops / Hung Firmware

If the firmware enters an infinite loop (bug), the harness detects that no state changes occurred over N million cycles and reports "MCU appears stuck." The frontend shows a warning. The user can reset or ask the Setup Agent to fix the firmware.

### Boot Verification (Automated Smoke Test)

After spawning simavr, the harness runs a quick automated test before handing control to the user:

1. **Boot check** — Run 1 million cycles (~125ms). Verify the firmware reaches the end of `setup()` without hanging. simavr can detect when the program counter enters `loop()` for the first time.
2. **Output init check** — Verify that output pins are in expected initial states (LEDs off, IR idle). Log any pins that are HIGH unexpectedly.
3. **Button response check** — For each button: press for 100ms, release, run 200ms. Check if any output pin changed state. If no output changed for ANY button, warn: "firmware may not be reading inputs correctly."

If the boot check fails (firmware hangs in setup), feed the error back to the Setup Agent: "Firmware hangs during initialization at PC=0x1A4. The MCU never reaches loop()." The agent can fix the .ino and recompile.

This automated smoke test catches the most common firmware bugs **without any user interaction** — before the user even sees the simulation panel.

WebSocket messages (bidirectional, real-time):

- **Frontend → Backend:** `{"action": "press"|"release", "instance_id": "btn_power"}`
- **Frontend → Backend:** `{"action": "reset"}` (restart MCU)
- **Frontend → Backend:** `{"action": "pause"|"resume"|"step", "step_ms": 1}`
- **Backend → Frontend:** `{"pins": {"PB1": {"state": 1, "pwm": 255}, "PD6": {"state": 0}}, "cycle": 4821000, "time_us": 602500}`
- **Backend → Frontend:** `{"log": "IR carrier detected on PD6, duration: 562us"}`
- **Backend → Frontend:** `{"uart": "Debug: button 1 pressed\n"}` (if firmware uses Serial)

WebSocket gives us the low-latency bidirectional communication needed for interactive simulation. SSE is too slow (and one-directional) for real-time button press → LED response.

### Building / Installing simavr

simavr is a C project (MIT license, actively maintained). Build requirements:

- **On dev machine (Windows):** Cross-compile with MSYS2/MinGW, or use WSL
- **In Docker:** `apt install libelf-dev gcc make` then `make` in simavr source
- **Pre-built binary:** We can vendor a pre-compiled `simavr_harness` binary for each platform

The harness itself is ~200 lines of C that links against libsimavr. It compiles to a single binary with no runtime dependencies beyond libelf.

```bash
# One-time build
cd tools/simavr_harness
gcc -o simavr_harness main.c -lsimavr -lelf -lpthread
```

For the Docker deployment, we add simavr to the build stage.

## Edge Cases & Considerations

- **No MCU in circuit** — Skip the setup step entirely. Some devices might be purely passive (e.g., a battery-powered LED with a switch, no microcontroller). The step should detect this and mark itself as "skipped — no programmable component."

- **Multiple MCUs** — Not supported now (catalog only has ATmega328P). If we add more MCUs later, the agent would need to generate separate firmware per MCU. For now, assume exactly 0 or 1 MCU.

- **Complex behaviors** — Some devices might need state machines (e.g., "hold button 3 seconds to enter programming mode"). The LLM is actually good at this — the device_description from the design agent should capture these behavioral requirements. If it doesn't, we might need the setup agent to ask the user for clarification (future enhancement).

- **Code size limits** — ATmega328P has 32KB flash. Most simple-device firmware is well under 10KB. The compile step will catch "sketch too large" errors naturally.

- **No crystal oscillator** — Our devices use the ATmega328P's internal 8MHz RC oscillator (no external crystal on the PCB). This matters for timing-sensitive operations (IR carrier frequency, serial baud rates). The system prompt should mention this constraint.

- **Existing firmware generator** — The current `firmware_generator.py` and `UniversalIRRemote.ino` template become obsolete once this agent is working. They can be kept as a fallback or reference, then removed.

- **simavr accuracy** — simavr is cycle-accurate for core AVR instructions and has good peripheral models (GPIO, timers, UART, SPI, ADC). It doesn't model analog characteristics (voltage levels, rise times) but that doesn't matter for digital firmware testing.

- **Simulation latency** — simavr runs faster than real-time on modern hardware (a 16MHz AVR simulates at ~100–500MHz equivalent). The bottleneck is the stdin/stdout IPC, but JSON-over-pipe at 60Hz is trivially fast. The user will see sub-frame response times for button presses.

- **IR protocol verification** — simavr simulates Timer2 faithfully, so the 38kHz PWM carrier and NEC/Samsung/Sony protocol timing are accurate. The harness can decode the IR signal and report the actual protocol + command code in the log, so the user can verify "is this really sending Samsung Power ON?"

- **Long-running simulations** — The simavr process stays alive as long as the user is on the simulation page. When they navigate away or the session expires, the SimulationManager kills the subprocess. Memory usage is minimal (~2MB for ATmega328P simulation).
